一、索引概述
定义：索引是对数据库表中一列或多列的值进行排序的一种数据结构，帮助MySQL高效获取数据。

类比：类似书籍的目录，通过目录快速定位内容，而不必逐页翻阅。

优点：加快查询速度（SELECT、WHERE、JOIN、ORDER BY等）。

缺点：占用额外存储空间；降低INSERT、UPDATE、DELETE的速度（因为索引也需要维护）。

二、索引的底层数据结构
存储引擎	主要索引结构	说明
InnoDB	B+Tree	主键索引叶子节点存储整行数据，辅助索引叶子节点存储主键值（聚簇索引）
MyISAM	B+Tree	索引与数据分离，叶子节点存储数据行地址（非聚簇索引）
Memory	默认Hash，也支持BTree	Hash索引适合等值查询，不支持范围查询
B+Tree特点：多路平衡树，所有数据存在叶子节点，且叶子节点间有双向指针，适合范围查询。

Hash索引：仅对等值查询有效，无法用于排序、模糊匹配。

三、索引类型
主键索引（PRIMARY KEY）

特殊的唯一索引，不允许有空值。

一张表只能有一个主键索引。

InnoDB中主键索引即为聚簇索引。

唯一索引（UNIQUE）

索引列的值必须唯一，但允许有一个NULL值（不同存储引擎对NULL处理可能不同）。

适用于保证数据唯一性。

普通索引（INDEX 或 KEY）

最基本的索引，没有任何限制。

加速查询，但不要求唯一性。

全文索引（FULLTEXT）

用于大文本字段的全文搜索（如CHAR、VARCHAR、TEXT）。

MyISAM和InnoDB（MySQL 5.6+）支持。

通过 MATCH AGAINST 语句使用。

组合索引（复合索引）

在多个列上建立的索引。

遵循 最左前缀原则。

四、索引创建与管理
sql
-- 创建表时定义索引
CREATE TABLE table_name (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    INDEX idx_name (name)          -- 普通索引
);

-- 在已有表上添加索引
CREATE INDEX idx_name ON table_name (column1, column2);  -- 组合索引
ALTER TABLE table_name ADD UNIQUE INDEX idx_unique (column);

-- 删除索引
DROP INDEX idx_name ON table_name;
ALTER TABLE table_name DROP INDEX idx_name;

-- 查看索引
SHOW INDEX FROM table_name;
五、索引使用原则与优化
1. 何时使用索引
频繁作为查询条件的字段（WHERE子句）。

经常用于连接的字段（JOIN ON）。

需要排序的字段（ORDER BY）。

用于聚合函数的字段（如GROUP BY）。

字段值分布范围广（重复值少）时索引效果好。

2. 何时避免索引
表数据量很小（全表扫描更快）。

字段值大量重复（如性别字段，只有男/女）。

频繁更新的字段（索引维护代价高）。

很少在查询中使用的字段。

3. 最左前缀原则
对于组合索引 (a, b, c)，以下查询可以使用索引：

WHERE a = 1

WHERE a = 1 AND b = 2

WHERE a = 1 AND b = 2 AND c = 3

WHERE a = 1 ORDER BY b （排序也利用索引）

WHERE b = 2 不会使用该索引（跳过最左列）。

注意：如果查询条件跳过了索引中的某一列，后面的列无法使用索引（但前面的列仍可用）。

4. 覆盖索引
如果索引包含了查询所需的所有列（即查询的字段都在索引中），则无需回表，直接通过索引返回结果。

可通过 EXPLAIN 的 Extra 列看到 Using index。

5. 索引下推（Index Condition Pushdown, ICP）
MySQL 5.6+ 优化，在遍历索引时，对索引中包含的字段先做条件过滤，减少回表次数。

EXPLAIN 的 Extra 列显示 Using index condition。

6. 索引失效的常见情况
对索引列使用函数或运算：WHERE SUBSTR(name,1,3) = 'abc' → 改写为 WHERE name LIKE 'abc%' 可使用索引。

隐式类型转换：如字符串列与数值比较，WHERE varchar_col = 123（列类型为varchar）会导致索引失效。

LIKE 以通配符开头：'%abc' 无法使用索引，'abc%' 可以。

使用 OR 且两边条件不是全部有索引（或优化器认为全表扫描更快）。

负向查询：NOT IN、!= 通常不走索引（取决于数据分布，有时也可能走）。

组合索引未遵循最左前缀。

六、索引优化实战技巧
使用 EXPLAIN 分析查询

sql
EXPLAIN SELECT * FROM table WHERE ...;
关注 type（访问类型，const/ref/range/index/all 从好到差）、key（实际使用的索引）、rows（扫描行数）、Extra（额外信息）。

选择合适的列作为索引

优先考虑高选择性的列（区分度高）。

字符串列可考虑前缀索引（INDEX (col(10))）节省空间。

冗余索引与重复索引

避免建立重复索引（如已有了 (a) 再建 (a,b) 可能冗余）。

删除长期不用的索引。

利用索引排序

ORDER BY 字段与索引顺序一致可避免文件排序（Using filesort）。

例如索引 (a,b)，ORDER BY a,b 可用索引排序，ORDER BY b,a 则不能。

联合索引设计

将等值查询的列放在前面，范围查询的列放在后面。

例如 WHERE a=1 AND b>2，索引 (a,b) 优于 (b,a)。

避免使用 SELECT *

只查询必要的字段，增加覆盖索引的可能性。

定期维护索引

对于B+Tree索引，随着数据增删可能产生碎片，可通过 ALTER TABLE table_name ENGINE=InnoDB; 或 OPTIMIZE TABLE 重建。

七、索引的代价
存储空间：每个索引都是一棵B+Tree，占用磁盘空间。

DML性能影响：每次插入、更新、删除都需要同步修改索引，影响写性能。

优化器选择：过多的索引可能让优化器选错索引，需人工干预（如使用 FORCE INDEX 或 USE INDEX 提示）。

八、不同存储引擎索引特点
特性	InnoDB	MyISAM	Memory
索引类型	B+Tree（聚簇）	B+Tree（非聚簇）	默认Hash，可选BTree
辅助索引存储	存储主键值	存储行指针	-
支持全文索引	5.6+支持	支持	不支持
事务支持	支持	不支持	不支持（表锁）
九、经典问题与解答
Q1：为什么主键通常建议用自增整数？
A：InnoDB的聚簇索引按主键顺序组织，自增主键能保证新数据顺序插入，减少页分裂，提高写入性能。

Q2：联合索引 (a,b) 和单独索引 (a) 有什么区别？
A：(a,b) 可同时加速 a 和 a+b 的查询，而 (a) 只加速 a 的查询。若已有 (a,b)，再单独建 (a) 是冗余的（但 (b) 不是冗余）。

Q3：如何判断索引是否有效？
A：使用 EXPLAIN 查看 key 列，以及 rows 估算扫描行数是否大幅减少。

Q4：字符串类型索引如何优化？
A：可建立前缀索引，例如 ALTER TABLE ADD INDEX (name(10))，只对前10个字符索引，节省空间。但需注意前缀索引不能用于 ORDER BY 和 GROUP BY。

十、总结
索引是双刃剑，合理设计能极大提升查询性能，滥用则拖慢写入。

理解B+Tree结构、最左前缀原则、索引失效场景是优化的基础。

日常开发中养成分析慢查询的习惯，结合 EXPLAIN 调优。

没有万能的索引方案，需根据实际业务的数据分布、查询模式权衡设计。

掌握以上知识点，你已经能够应对大多数MySQL索引相关问题。实践中多动手分析，积累经验，才能更好地发挥索引的作用。
